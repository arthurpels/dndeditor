# PRD: Усложнения после MVP для D&D Editor

Дата: 2026-07-04  
База: текущий MVP уже закрывает создание персонажа, карточку, сохранение, импорт/экспорт и библиотеку.

## 1. Цель

После MVP нужно добавить полезные расширения, не ломая основной сценарий:

`Home → Create → Review → Save → Open later → Edit`

Приоритет — улучшения, которые повышают удобство, полноту и демонстрационную ценность продукта, но не требуют серверной синхронизации как обязательного условия.

## 2. Что считаем усложнениями

В рамках этого этапа делаем:

1. Систему подсказок и onboarding внутри мастера создания персонажа.
2. Хоумбрю-расширения: возможность добавлять свои расы и классы.
3. Генерацию биографии персонажа по его параметрам.
4. Подготовку архитектуры под будущую серверную синхронизацию или отдельный storage-flow, если успеваем.

## 3. Общие требования

- Не ломать MVP-сценарий.
- Не менять формат уже сохранённых персонажей без обратной совместимости.
- Все новые данные должны сохраняться локально.
- Новые функции должны быть изолированы по слоям: UI / state / domain / storage.
- Любую часть, которая может быть выполнена независимо, нужно делать без блокировки других задач.

## 4. Разделение работы на 4 разработчиков

Ниже задачи разбиты так, чтобы каждый разработчик получил свою зону ответственности и понятный конечный результат.

---

## Dev A — Подсказки и onboarding

### Зона ответственности

- подсказки внутри wizard;
- интерактивные пояснения по сложным шагам;
- мягкое сопровождение пользователя;
- локальные help-тексты и first-run experience.

### Что нужно сделать

1. Добавить подсказки на шаге Basics:
   - что такое race;
   - что такое class;
   - что такое background.

2. Добавить подсказки на шаге Abilities:
   - объяснение Standard Array;
   - объяснение Point Buy;
   - объяснение 4d6 drop lowest;
   - пояснение, почему некоторые значения недоступны.

3. Добавить подсказки на шаге Skills:
   - как работает выбор навыков;
   - почему background skills уже выбраны;
   - почему нельзя выбрать больше лимита класса.

4. Добавить подсказки на Review:
   - что именно будет сохранено;
   - какие поля можно изменить позже;
   - что такое current HP и biography.

5. Если возможно, сделать первый экран onboarding:
   - короткий welcome;
   - кнопка “Понятно, начать”.

### Результат

- пользователь не теряется в wizard;
- сложные правила объяснены прямо в интерфейсе;
- меньше вопросов по логике D&D.

### Acceptance criteria

- подсказки не мешают основному сценарию;
- wizard проходит без обязательного чтения help;
- все подсказки локализованы на русский;
- UI не перегружен длинными текстами.

### Prompt-ready task

> Добавь в Flutter-приложение подсказки и onboarding для мастера создания персонажа D&D.  
> Нужны краткие пояснения на шагах Basics, Abilities, Skills и Review.  
> Сделай так, чтобы подсказки были ненавязчивыми, локальными и не ломали основной flow.  
> Сохрани текущую архитектуру: UI отдельно, логика отдельно.

---

## Dev B — Хоумбрю: свои расы и классы

### Зона ответственности

- создание пользовательских рас;
- создание пользовательских классов;
- хранение homebrew локально;
- подключение homebrew к wizard и библиотеке.

### Что нужно сделать

1. Добавить UI для создания собственной расы:
   - название;
   - скорость;
   - бонусы к характеристикам;
   - описание.

2. Добавить UI для создания собственного класса:
   - название;
   - hit die;
   - saving throws;
   - количество навыков;
   - доступные навыки;
   - описание.

3. Сохранение homebrew в локальном хранилище.

4. Подмешивание user-defined race/class в списки выбора wizard.

5. Показать отличия homebrew от стандартных PHB-данных.

### Важные ограничения

- Не ломать стандартные рассы и классы.
- Homebrew должен быть опциональным.
- Если пользователь не создавал свои сущности, приложение работает как раньше.

### Результат

- пользователь может расширять игру под свою кампанию;
- приложение становится более полезным для кастомных столов.

### Acceptance criteria

- можно создать новую race и class;
- они появляются в выборе при создании персонажа;
- они сохраняются после перезапуска;
- стандартный контент продолжает работать.

### Prompt-ready task

> Реализуй в Flutter local homebrew editor для D&D Editor: пользователь должен уметь создавать свои расы и классы.  
> Нужны формы ввода, локальное сохранение, интеграция в wizard и обратная совместимость с базовыми PHB-данными.  
> Сделай архитектуру так, чтобы homebrew не ломал стандартный контент.

---

## Dev C — Генерация биографии и контент-подсказки

### Зона ответственности

- генерация биографии персонажа;
- шаблоны по race/class/background/skills;
- кнопка автозаполнения biography;
- ручная правка результата.

### Что нужно сделать

1. Добавить генератор биографии:
   - на основе расы;
   - на основе класса;
   - на основе background;
   - с учётом выбранных навыков и ключевых статов.

2. Подготовить несколько шаблонов биографии:
   - нейтральный;
   - героический;
   - мрачный;
   - авантюрный.

3. Встроить генерацию в Review или отдельный экран/секцию.

4. После генерации дать пользователю возможность отредактировать текст.

5. Не использовать внешние сервисы на этом этапе, если можно решить локально шаблонами.

### Результат

- у персонажа появляется более живой профиль;
- продукт выглядит более “законченным” без серверной зависимости.

### Acceptance criteria

- биография генерируется локально;
- текст не пустой и не выглядит случайным мусором;
- пользователь может отредактировать и сохранить результат;
- генерация не ломает существующий draft/save flow.

### Prompt-ready task

> Добавь в Flutter-приложение локальную генерацию биографии персонажа D&D.  
> Генератор должен использовать race, class, background и навыки, работать без сервера и позволять пользователю вручную редактировать результат.  
> Сделай несколько шаблонов и аккуратную интеграцию в экран обзора или карточку персонажа.

---

## Dev D — Архитектура под синк, storage и интеграцию

### Зона ответственности

- подготовка к серверной части;
- расширение storage;
- архитектурная чистота;
- интеграция новых сущностей в repository / app bootstrap;
- контроль за тем, чтобы не было заглушек вроде “не подключено”.

### Что нужно сделать

1. Проверить и упростить repository-слой:
   - чтобы он был готов к будущей синхронизации;
   - чтобы локальные операции были изолированы;
   - чтобы формат данных был стабильным.

2. Подготовить точки расширения для будущего backend:
   - интерфейсы;
   - адаптеры;
   - возможность подмены источника данных.

3. Убрать любые оставшиеся UX/tech-заглушки, которые мешают ощущению завершённости.

4. Привести bootstrapping app к понятной последовательности:
   - load repository;
   - load ready-made characters;
   - open Home.

5. Если появится время — подготовить минимальный contract для будущего API без реализации сервера.

### Результат

- архитектура готова к росту;
- приложение не завязано жёстко на один источник хранения;
- потом можно легко добавить сервер без переписывания UI.

### Acceptance criteria

- локальное хранилище работает стабильно;
- архитектурные зависимости понятны;
- новая функциональность не ломает current save/load;
- приложение запускается без остаточных “не подключено” сообщений.

### Prompt-ready task

> Подготовь архитектуру Flutter-приложения D&D Editor под дальнейшую синхронизацию и расширение хранилища.  
> Нужны чистые интерфейсы для repository/storage, аккуратный bootstrap приложения и отсутствие заглушек в пользовательском UI.  
> Не добавляй серверную реализацию, только подготовь слои и точки расширения.

---

## 5. Рекомендуемый порядок выполнения

1. Dev A — подсказки и onboarding.
2. Dev B — homebrew расы и классы.
3. Dev C — генерация биографии.
4. Dev D — архитектурная подготовка под синк и storage.

Если мало времени, можно делать параллельно:

- Dev A и Dev C — почти не конфликтуют;
- Dev B и Dev D — надо чуть аккуратнее из-за shared models/repository.

## 6. Definition of Done для этапа усложнений

- подсказки работают;
- homebrew можно создать и выбрать;
- биография генерируется и редактируется;
- архитектура не ломает MVP;
- после перезапуска всё сохраняется;
- тесты зелёные;
- старый функционал остаётся рабочим.

## 7. Формат работы с ИИ

Если отдаёшь задачу мне или Клоду, лучше использовать такой шаблон:

> Ты работаешь над Flutter-приложением D&D Editor.  
> Нельзя ломать текущий MVP.  
> Твоя задача — [конкретный пункт].  
> Работай только в своей зоне ответственности: UI / state / repository / rules.  
> Если нужно менять общие модели, сначала опиши влияние на другие модули.  
> В конце дай список изменённых файлов и кратко объясни, что проверил.
